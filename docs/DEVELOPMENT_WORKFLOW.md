# 日常开发与 Git 工作流

本流程面向维护者和 Codex。目标是让每轮开发有清楚的起点、可独立回退的提交和可核对的交付结果。长期有效的数据与隐私边界仍以根目录 [AGENTS.md](../AGENTS.md) 为准；版本命名见[版本基线](RELEASE_MODEL.md)。

## 1. 开始一轮任务

1. 查看 `git status --short --branch`、`git worktree list` 和相关代码。先识别用户已有的未提交内容，不用强制重置来“清洁”工作树。
2. 更新已知基线：`git fetch --no-tags origin main`，确认 `origin/main` 的提交与发布标签。仓库存在历史同名标签差异时，不能为了一次拉取强制覆盖标签。
3. 普通功能、修复、设计和文档从 `origin/main` 建 `codex/<任务>` 分支。确实需要并行工作时再开独立 worktree；一个工作树只服务一个明确任务。
4. `develop` 与 `exp` 是历史分支；`exp` 的独有提交及 `-expN` 标签是可追溯资料，不再接受新普通功能。确需恢复单项历史实验时，从当前 `main` 单独挑选并重新验证。

## 2. 实现与提交

- 先确认根因与受影响的功能边界，再改代码。历史调查报告只提供线索，不替代当前代码、构建配置或设备证据。
- 每个提交对应一个可解释、可回退的变化。用户在同轮追加独立问题时保留提交边界；不要把顺手清理或重排混入功能修复。
- 运行与风险相称的编译、定向测试或设备验证；纯文档检查链接、事实和 diff 即可。不要用无关的大套件代替关键场景。
- 暂存前先看 `git diff --check`、`git diff --stat` 和 `git status --short`，用 `git add -- <本次文件>` 精确暂存。`SleepDown-Server/`、密钥、数据库、设备原始数据、临时截图、日志、APK 和构建缓存不得入库。
- 本地工作成果可以保留在任务分支供审阅。只有用户授权远端操作时才推送或创建 PR；PR 授权包含为该 PR 的提交、推送和后续更新，不包含合并或发布。

## 3. PR、合并和发布

1. 普通改动的 PR 目标为 `main`。描述说明变化原因、主要文件、验证证据和已知限制；GitHub 元数据用 Codex GitHub plugin 操作。
2. 合并后拉取 `main`，确认本地 `main` 快进到远端提交；不要在旧功能分支上接下一件事。需要同轮后续修复时，可保留该分支的独立提交并继续同一 PR。
3. Beta 与正式版按[版本基线](RELEASE_MODEL.md)处理应用内日志、发布页、标签和附件。发布是单独动作，未获授权时只准备可审查的候选结果。
4. 发布后记录实际构建、签名、包身份、设备和用户可见结果。失败的实验写入对应报告，不变成全局禁令。

## 4. 收尾与定期整理

- 先确认 worktree **干净且不被任务使用**，再移除；有未提交内容时保留原处或明确归档补丁。不要把清理 worktree 当成删除用户更改的理由。
- 已完全进入 `main` 的短期本地分支可删除；含独有提交的停用分支先建立带日期的 `archive/` 引用和索引，再从日常分支列表移出。公开标签和已发布历史不重写。
- 临时日志、崩溃回放和 Bug 定位截图在结论进入报告后删除；精选的阶段画面存放在仓库外的私有开发历程文件夹。APK、数据库和凭据按数据性质分别处理，不把它们塞进图片归档。
- 清理结束再看一次 `git status --short --branch`、worktree 和分支列表。凡仍有未提交内容、活动任务或特殊依赖的路径，在交接中写明，不假装已清空。
