# 开发、提交、PR 与合并规范

本流程供维护者、贡献者和各类 AI 助手共同使用。数据与隐私边界见 [AGENTS.md](../AGENTS.md)，外部贡献的 Fork 与构建步骤见 [CONTRIBUTING.md](../CONTRIBUTING.md)，版本与发布见 [RELEASE_MODEL.md](RELEASE_MODEL.md)，当前未完成工作见 [AI_HANDOFF.md](AI_HANDOFF.md)。本文定义流程，不把历史分支或某次验收结论当作长期规则。

## 1. 接手与确定基线

先完整阅读 `AGENTS.md`，接续任务再读交接页和对应 PR。执行只读盘点：

```powershell
git status --short --branch
git log -5 --oneline
git worktree list
git remote -v
git stash list
```

确认当前任务、分支、已有改动和其他工作树的用途。工作目录干净不代表 stash、忽略文件或其他任务已清理；不为切换助手强制重置、自动 pop stash 或移动其他任务。

在允许联网的环境更新上游引用：维护者使用 `git fetch --no-tags origin main`；Fork 贡献者使用 `git fetch --no-tags upstream main`。不强制覆盖发布标签。无法联网时记录本地引用的核对时间，不声称已同步最新代码。

| 场景 | 分支选择 |
| --- | --- |
| 新的独立功能、修复或文档任务 | 从最新上游 `main` 创建短期分支，PR 目标为 `main` |
| 同一未合并 PR 的反馈或换助手续做 | 复用该 PR 分支，先核对远端 head 与本地差异，不从 main 重做一遍 |
| 多项确实独立的工作 | 各自分支，必要时独立 worktree；不要让多个任务同时修改同一工作树 |
| 依赖另一未合并 PR | 在描述中列出依赖和最终目标；依赖合并后核对完整 diff，避免把依赖误算为新改动 |
| 正式版源码领先 main 等历史欠账 | 先核对提交关系和已有回流 PR；明确实际基线与多出的已发布提交，再选择续做或独立回流，不能把任务分支快进写成 main 已更新 |

维护者默认使用 `codex/<任务>`；外部贡献者不强制前缀。`develop`、`exp` 和 `-expN` 仅供追溯，恢复单项历史功能时从当前有效基线单独挑选。当前 main 与正式版的实际关系见版本基线和交接页；没有合并授权时，完成候选与记录，不顺带改写 main。

## 2. 修改与提交

先查看相关代码与实现证据，围绕用户目标修改。一个提交表达一个可说明、可回退的变化；同轮追加独立问题保留提交边界，纯格式化、文档整理与功能修改在合适时分开提交。

提交标题直接写清动作和对象，中英文均可。可用 `fix:`、`feat:`、`docs:`、`ci:` 等前缀，但不强制格式、Issue 编号或提交数量。保留真实作者和第三方来源；AI 辅助不能替代提交者审阅，也不能把未执行的验证写成通过。

提交前检查并精确暂存：

```powershell
git status --short
git diff --stat
git diff --check
git add -- <本次文件>
git diff --cached --stat
git diff --cached
git diff --cached --check
git commit -m "说明本次变化"
```

命令中的占位符需替换为实际文件。第三方 `.patch` 的必要空白上下文按 [补丁说明](../patches/README.md)检查，不为消除空白提示破坏补丁格式。

`SleepDown-Server/`、密钥、数据库、设备原始数据、临时日志和截图、APK、构建缓存不得入库。用户明确指定的公开素材先核对来源与隐私。不要用 `git add .` 代替范围审阅。

未推送的个人分支可按需要整理提交。已共享的 PR 分支默认追加修复提交；需要更新基线时优先合并上游 main。重写已共享历史或强推须有明确授权，不因换助手或追求整齐自动 rebase、amend 或 force push。

## 3. 最小充分验证

本地验证入口统一以 [AGENTS.md 的验证表](../AGENTS.md#验证与安装)为准。外部贡献无需维护者签名，按贡献指南构建 Debug。纯文档核对事实、相对链接和 diff，不跑 Android 构建；局部样式和可逆交互不机械追加测试。数据、时间规则、解析和状态机才按实际风险选择定向测试或真实场景。

记录实际命令、结果和对应代码提交；设备验证还记录系统、设备与场景。旧 APK、旧代码的通过结果不能覆盖新代码；后续仅改文档时可引用原代码验证点。构建通过、单元测试通过、已安装和用户验收分别记录，不能互相替代。

## 4. 创建和维护 PR

远端操作须在用户授权范围内。“开 PR”包含该 PR 所需的提交、推送、审查修复和后续更新，不包含合并、标签、Release 或部署。“打包安装”包含构建与覆盖安装。用户明确认定发布哪个版本的 Release 时，按 [AGENTS.md](../AGENTS.md) 完成对应 PR 的审查与合并，不能发布后留待再次授权。已有授权跨助手和会话继续有效；交接记录其来源，不重复确认。仅要求修改时先完成可审查的本地成果。

Codex 的 GitHub 元数据操作使用自带 GitHub plugin，不使用 GitHub CLI；其他助手使用环境中已授权的集成。Git fetch/push 使用 Git。插件不支持 Release 写入或附件上传时，按 [AGENTS.md](../AGENTS.md) 中用户已确认的本地凭据发布规则处理，不转到浏览器、不重复索取已有授权；不使用无关凭据或绕过权限。

普通改动面向 `main`。按[统一模板](../.github/pull_request_template.md)写清：

- 触发问题、原有行为和最终变化；标题与描述反映最终实现。
- 需要时说明基线、依赖 PR、额外已发布提交和数据兼容影响。
- 实际验证及对应提交、尚未验证的关键场景、交付产物和验收状态。

同一目标继续更新原 PR；新增独立目标另开分支与 PR。推送前检查未推送提交和完整 PR diff，避免把其他任务带入。创建后保存 PR 链接；Codex 还需将其附加到当前任务。

### 草稿、评审与 Actions

| 状态 | 使用方式与检查 |
| --- | --- |
| 本地进行中 | 范围尚未清楚或未获远端操作授权，先保留本地提交 |
| Draft | 开发迭代、等待设备反馈或还有未完成项；跳过自动 PR 检查，仍可能显示一条 skipped run |
| Ready for review | 实现与必要验证已完成，未完成项有明确说明，开始请求维护者评审与完整 CI |
| 已合并 | 改动进入 main；不等于已打包、安装或发布 |
| 已关闭但未合并 | 说明撤回、重复或已发布覆盖的证据，保留需要追溯的历史 |

工作流源于 [pr-checks.yml](../.github/workflows/pr-checks.yml)：草稿跳过，`ready_for_review` 开始检查；可评审 PR 在打开、重开和推送时检查，同一 PR 的新运行取消旧运行。不要用保持草稿来掩盖待修复的失败；应记录原因和下一步。

是否运行 Android job 依据**整个 PR 相对基线的 diff**，不是最后一笔提交的标题。纯文档 PR 跳过 Android；Android PR 的末尾追加文档仍属于 Android PR。Android job 包含 Release Kotlin 编译、现有定向测试集合和无正式签名的 Debug 打包；不能仅根据 job 名称“Android compile”认为只有编译。确切命令与筛选范围以工作流为准。

`skipped` 表示未执行，不能当作测试通过。首次 Fork 工作流可能需要维护者批准；批准运行检查不等于批准合并。GitHub 的通知偏好不由 PR 草稿规则代替。

## 5. 评审与合并

外部贡献由维护者审阅后合并；维护者继续使用已有仓库和管理员权限，无需 Fork 或批准自己的 PR。批准人数、必需检查、CODEOWNERS 审查及管理员豁免以 GitHub 实时配置为准，文档不视为已修改保护规则。CI 是否被平台设为必需检查，与本流程要求核对真实失败是两件事。

取得合并授权后，针对**将要合入的 PR head**核对最终 diff、讨论、CI 和关键验收；处理真实失败，说明未执行项。权限允许跳过检查不等于问题已解决。若还需用户决定，先完成候选、验证和风险说明，让用户审阅具体结果。

本项目的默认选择与例外如下；这是协作约定，不自动改变 GitHub 的合并选项设置：

| 方式 | 使用规范 |
| --- | --- |
| Create a merge commit（默认） | 保留有意义的提交边界、作者与原始 SHA；发布基线回流、包含已发布祖先或多项独立修复时使用 |
| Squash and merge | 单一小问题且分支包含大量临时提交时可用；合并说明保留真实贡献者和必要来源，合并后从新 main 创建下一分支 |
| Rebase and merge | 有明确线性历史需求时再选；会改变提交 SHA，不用于保留发布标签祖先关系的回流 |

GitHub 三种方式的行为见[官方说明](https://docs.github.com/en/pull-requests/reference/pull-request-merges)。默认不 squash 已发布源码的回流，避免 main 的版本归属与发布祖先关系继续分离。不能为遵循默认方式覆盖平台当前规则；遇到冲突先给出具体影响。

合并前再次确认 PR 号、目标分支和 head 未被其他任务更新；通过集成支持的预期 head 校验或回读核对，避免将新追加但未审阅的改动带入。只报告平台已确认的合并结果与合并提交。

合并后 fetch main，核对合并提交已进入远端 main；本地 main 仅在干净且未被其他任务占用时快进同步。下一个独立任务从新 main 开始；**同一 PR 的追加修复只适用于它尚未合并时**。已合并分支不继续承载新任务，尤其不能在 squash 后沿旧分支反复开 PR。

## 6. 发布与清理

合并和发布分别授权。Beta 与正式版按版本规范处理日志、包身份、签名、标签、附件和公开回读。默认从已进入 main 的验证提交发布；确有已授权的例外时，记录源码 SHA、与 main 的关系和回流安排。发布完成后核对发布提交可从 main 到达，未回流时在交接中保留待办，不声称已收口。

删除本地/远端分支、worktree 或 stash 前确认精确对象、授权、独有提交和活动任务。已合并也不代表工作树无未提交数据；squash 后需检查补丁覆盖，不能仅凭祖先判断。已发布标签与历史不改写；有保留价值的停用内容先明确归档位置。

收尾检查 `git status --short --branch`，说明已提交/推送、PR 状态、构建与安装结果及遗留事项。没有检查的其他工作树不得宣称干净。临时诊断结论写入对应报告后，按授权处理临时文件，不把数据或 APK 混进图片归档。

## 7. 更换助手与交接维护

阶段交付、切换助手或任务结束时，更新 [AI_HANDOFF.md](AI_HANDOFF.md)中对应任务，按以下顺序保留必要事实：

1. 更新时间、当前目标、工作分支、PR、实际基线和相关代码提交。
2. 已完成事项与尚未完成的下一步，明确哪些依赖用户实机验收。
3. 用户已授权的动作及可追溯来源；未授权的合并、发布等边界。原始指令不可访问时不得单凭交接文档扩大权限。
4. 实际运行的验证、代码锚点、产物和安装状态；不要把本地临时路径写成别人一定可用的交付位置。
5. 需要保留的未提交修改、stash 名称、其他工作树及相关报告。stash 按名称定位，序号可能变化。

交接页保留当前必要信息，历史细节引用报告；规则变化更新所属规范。并行任务分别记录分支和报告，不覆盖其他任务。接手者先核对实际 Git/PR 状态，沿已有成果继续，只重做与新变化、失败或证据缺口相关的验证。
