# 本机 ADB 入口与无线连接调查

日期：2026-10-04。用户要求彻查本机 ADB，并修复以后默认调用的通道。

## 调查结论

- `5037` 由 OPPO 互联的 SYSTEM ADB 占用，`5038` 由当前用户的 Android SDK ADB 占用。两个服务器的设备列表独立，调查开始时均未列出在线设备。
- 原 SDK 版本为 `37.0.0`，默认发现后端 `LIBADBMDNS`，mDNS 已启用；对比重启及 `OPENSCREEN` 后端也未发现设备。
- SDK 的 TCP / UDP 防火墙规则在当前 Public 网络启用放行，系统 mDNS 入站规则也启用。目标网段走 WLAN，未被 VPN 路由接管。
- WLAN 上对原设备 IP 的邻居解析为 `Unreachable`，ICMP 未收到回复，直接从 WLAN 发出的 ADB mDNS 查询也未收到回复。上述证据尚不能区分手机地址变化、手机无线调试状态和网络侧隔离，不据此宣称已修复设备连接。
- 用户确认其“仍然连接”的依据是手机无线调试的“已配对设备”列表。配对授权保留与 ADB 当前在线是两个状态。
- 原生 `adb connect` 连接失败时可能仍返回 `0`，原项目入口直接透传退出码，容易把失败当作成功。

## 已完成修复

- 通过官方 `sdkmanager` 将 SDK Platform-Tools 更新至 `37.0.1-15733141`。更新前备份 `platform-tools` 至仓库外 `C:\Users\23085\.codex\backups\adb-2026-10-04\platform-tools-37.0.0`，最终恢复默认 `LIBADBMDNS`，关闭诊断 trace。
- 用户环境固定 `ADB_SERVER_SOCKET=tcp:127.0.0.1:5038` 与 `ANDROID_ADB_SERVER_PORT=5038`，后者供 Android Studio / DDMLib 使用。已运行的应用须重启以继承用户环境。
- PowerShell 7 / Windows PowerShell 5 的 `adb` 从单纯别名改为调用项目 `scripts/Invoke-Adb.ps1`，显式指定 SDK 和 `-P 5038`。CMD 使用 SDK PATH 与用户环境。
- 项目入口对 `connect` 的输出核验 `connected to` / `already connected to`；未成功连接时返回失败码，兼容命令前的 ADB 全局选项。继续保留配对密钥与已知设备，不替换身份。

## 实际验证

- 新 PowerShell 7、Windows PowerShell 5 和 CMD 执行 `adb server-status`，均访问 SDK `37.0.1` 的服务；服务器监听 `5038`。
- 对本机未监听的 `127.0.0.1:1` 发起连接，默认及显式 `-P 5038` 调用均得到失败退出码 `1`；Windows PowerShell 5 默认入口也确认失败码。
- OPPO 互联的 `5037` 服务器保留，本轮未终止该服务或修改其 SYSTEM 配对身份。
- 用户再次提供当前连接端口 `42533`。mDNS 发现恢复后按服务名连接完成 TLS 握手，但约 21 秒后连接再次断开，第一次安装因设备消失而未开始；这是实际掉线，未将短暂的在线当作稳定修复。
- 默认源地址与显式绑定 WLAN 的 TCP 对比中，先出现一次超时 / 成功差异；随后并行对比两者均成功，不能据此归因 VPN，未修改代理或 VPN 配置。
- 最终使用用户确认的当前 IP / 端口在 `5038` 重连，并在同次调用中覆盖安装签名 Release，返回 `Success`。PLJ110 实际系统为 Android 17 / SDK 37；随后 0、5、10、15、20、25、30 秒的设备状态均为 `device`，默认入口在该观察期间保持在线。
- 已完成本机默认入口、工具版本和失败退出码修复；30 秒观察不能保证手机休眠、网络切换或端口变化时永不掉线。手机配对授权继续保留。
